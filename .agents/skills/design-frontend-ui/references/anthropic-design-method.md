# Anthropic 主题驱动设计方法

本参考根据 Anthropic 官方 [`frontend-design`](https://github.com/anthropics/skills/tree/main/skills/frontend-design) 的核心思想重新整理，并适配本项目的组件复用与轻量开发要求。它不是上游原文副本。

## 读取条件

仅在以下条件同时成立时读取并使用：

- 正在设计新页面、独立体验或进行重大视觉重设计；
- 用户或设计稿没有完整规定视觉方向；
- 设计选择会明显影响产品辨识度。

局部样式修正、设计稿还原、后台常规表单和现有组件调整不要使用本流程。

## 第一遍：形成主题化方向

先确定一个具体主题、目标用户和页面的单一任务。列出该主题真实存在的材料、工具、对象、术语、工作环境和视觉符号，从中推导设计，不从流行组件效果反推业务。

形成一份轻量内部方案：

1. **颜色**：优先使用项目令牌；确需新方向时，定义 4 至 6 个有名称和用途的颜色。
2. **字体**：优先使用项目字体；独立新界面才为标题、正文、数据或辅助信息分别确定角色。
3. **布局**：用一句话说明阅读顺序。只有存在多个合理结构时才画简短 ASCII 草图比较，不默认输出正式设计文档。
4. **标志性元素**：选择一个最能体现主题、会被记住的元素，例如独特的信息组织、素材、互动或排版处理。
5. **审美风险**：只承担一个可以说明业务理由的风险，其余区域保持克制。

不要默认使用与主题无关的奶油色衬线风、黑底荧光点缀、报纸式密集分栏、大数字加渐变或其他当下流行模板。用户明确要求这些方向时，以用户要求为准。

## 第二遍：在编码前自我批评

逐项检查：

- 把主题换成完全不同的产品后，这套方案是否仍然成立？若成立，说明它仍过于通用。
- 标志性元素是否来自主题，还是只因为某个组件看起来炫酷？
- 编号、眉题、标签、分隔线和装饰是否传达真实顺序、类别或关系？
- 真实内容是否贯穿页面，还是只在标题中提到主题？
- 动效是否集中服务一个关键时刻，还是散落成无意义效果？
- 实现复杂度是否匹配方向？极简设计依赖精确间距、字体和细节，不等于少写几行 CSS。
- 是否能删除一个配件而不损失信息？能删除就删除。

通过检查后再实施，并让代码遵循确定的颜色、字体、布局和标志性元素。注意 CSS 选择器优先级，避免通用类和元素选择器互相覆盖间距或排版。

## 界面文案检查

- 使用用户控制和认识的对象命名功能，不用系统内部术语。
- 使用主动语态和具体动词；按钮、加载状态和完成反馈保持同一动作名称。
- 错误信息指出问题与修复动作；空状态引导用户开始，而不是营造情绪。
- 保持句式、语气和术语一致，让每段文字只完成一个任务。

## 输出约束

大部分探索在内部完成。只有视觉方向需要用户决定时，才展示两到三个真正不同的候选方向；否则直接实现最佳判断。不要让设计计划本身拖慢交付。
