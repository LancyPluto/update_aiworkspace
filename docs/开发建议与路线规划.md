# 开发建议

更新时间：2026-05-17

## 下一阶段优先级

### 1. 先做真实生图闭环

优先验证 `seedance_images`：

1. 后台配置 seedance 生图模型。
2. 后台创建文生图工具和字段 schema。
3. 用户端提交文生图任务。
4. Worker 调用 `/v1/images/generations`。
5. 图片落盘到 `/generated/images/{taskId}/...`。
6. 用户端结果页展示图片。
7. 计费日志记录 `PER_CALL`、`billableUnits` 和平台成本。

这条链路能同时验证模型配置、多模态表单、worker、静态资源、任务状态机和计费。

### 2. 工具配置模板后台化

当前字段模板已经比原来稳定，但仍有部分模板逻辑在前端。建议下一步把常用模板沉淀成后端可复用配置：

| 类型 | 推荐模板 |
| --- | --- |
| 文案生成 | prompt、目标用户、风格、长度 |
| 文生图 | prompt、负面词、比例、数量、风格 |
| 视频生成 | prompt、比例、时长、参考图 |
| 数字人 | 脚本、声音、人物、背景、字幕 |

字段 schema 不建议完全按单个供应商 API 文档一比一暴露。更稳的方式是：

- 用户端字段保持产品化、中文友好。
- Worker/provider adapter 负责把产品字段映射到供应商 API 字段。
- 高级参数可以放到“高级设置”或 `providerOptionsJson`，避免普通用户看到一堆英文 API 参数。

## 前端合并规划

当前有两套前端：

| 项目 | 技术栈 | 现状 |
| --- | --- | --- |
| `user-web` | Vue 3 + Vite | 用户端体验，动态表单和任务结果页 |
| `admin-frontend` | Next.js + React | 管理后台，配置和运营页面 |

短期不建议马上强行重写。原因是当前后端、多模态、计费还在快速收敛，前端重写会放大风险。

推荐分三步：

### 阶段 1：先统一契约和设计资产

- 统一 API types 生成或维护方式。
- 统一 logo、颜色、按钮、表单、表格和状态组件规范。
- 把动态表单、结果渲染、模型配置这类复杂交互的字段契约稳定下来。

### 阶段 2：选择一个长期技术栈

如果团队偏全栈 React，建议统一到 Next.js：

- 管理后台已经是 Next.js。
- 后续 SEO、权限路由、服务端渲染、BFF、文件/媒体页面更容易统一。
- React 生态在复杂后台表单、数据表格、组件库方面选择更多。

如果团队 Vue 熟练度明显更高，也可以统一到 Vue + Vite：

- 用户端已经是 Vue。
- Vite 开发体验轻，迁移成本较低。
- 适合纯 SPA 工具平台。

判断标准不是“哪个框架更高级”，而是谁能更快稳定交付。当前项目更建议中期统一到 Next.js，但前提是先把接口和业务边界稳定。

### 阶段 3：迁移用户端

若决定统一 Next.js：

1. 保留 `user-web` 线上可用。
2. 在 `admin-frontend` 或新 `web` 项目中增加用户端路由。
3. 先迁移登录、工具列表、工具详情、任务状态、结果页。
4. 动态表单和结果渲染迁移完成后再下线 Vue 项目。

不要边改后端业务边做前端大迁移。

## Agent 边界控制

当前 Agent 方向要避免继续膨胀。建议定义成“工具编排层”，不是另一个业务后端。

### Agent 可以负责

- 意图识别。
- 推荐或选择工具。
- 根据工具 schema 生成参数。
- 调用 backend 内部接口创建任务。
- 订阅或轮询任务结果。
- 汇总多个工具结果，形成最终回复。

### Agent 不应负责

- 直接扣算力。
- 直接改任务状态。
- 绕过 backend 访问数据库。
- 自建一套工具配置和权限系统。
- 为了“像 Agent”而引入复杂框架。

### 是否继续保留 agent-service

短期建议：

- 保留代码，但不让它成为核心工具任务链路的必要依赖。
- 新能力优先在 backend + worker 主链路中闭环。
- 等工具调用闭环稳定后，再评估是否需要独立 agent-service。

如果 Agent 只是“提示词拼接 + 工具参数生成”，完全可以先放在 backend 或 worker 内做轻量实现。只有当出现长上下文、多步骤计划、文件工作区、并发工具调用等明确需求时，再考虑独立运行时。

## Provider 接入建议

新增模型供应商时不要把所有逻辑塞进通用 OpenAI-compatible：

- 文本模型：优先走 OpenAI-compatible 或 Anthropic-compatible。
- 图片模型：独立 provider adapter，返回统一 `images[]`。
- 视频模型：独立 provider adapter，支持异步轮询。
- 音频/语音：独立 provider adapter，处理二进制和 data URL。

统一的不是供应商 API，而是平台内部结果结构、任务状态和计费回写。

## 数据库和接口维护规则

每次后端字段变更必须同步：

1. Entity/DTO/Mapper。
2. `DataInitializer`。
3. `sql/*.sql` 初始化脚本。
4. `backend/src/test/resources/schema-test.sql`。
5. `docs/api/openapi.yml`。
6. 管理端和用户端 TypeScript 类型。
7. 至少一个后端测试或 worker 假任务测试。

这个规则比“写完能跑”更重要，因为团队其他人拉取代码后能不能直接启动，主要取决于这些地方是否同步。
