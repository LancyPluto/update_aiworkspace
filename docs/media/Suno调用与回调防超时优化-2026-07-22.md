# Suno 调用与回调防超时优化

更新日期：2026-07-22

适用域名：`https://wlcloudai.com`

适用范围：Suno 音乐生成、Worker、任务中心、Nginx、数据库迁移

## 1. 背景与问题结论

历史链路在 Worker 内同步提交 Suno 请求并持续轮询结果。创建请求使用 60 秒读取超时，一旦 Suno 已接收任务但 HTTP 响应没有在 60 秒内返回，Worker 会把本次调用判定为失败。此时会出现两边状态不一致：

- Suno 侧任务已经创建并最终生成成功；
- 本地没有保存 Suno `taskId`，也没有收到有效回调；
- 本地任务被标记为 `MODEL_TIMEOUT`，用户无法取得已生成结果；
- 若直接重试创建请求，还可能重复生成、重复扣费。

问题的关键不是必须改用 Redis，而是缺少以下可靠性能力：

1. 外部任务 ID 检查点；
2. 可持久化、可重放、幂等的回调入口；
3. 对“请求已发送但响应未知”的正确处理；
4. 回调与轮询协同的任务状态机。

现有 RabbitMQ 可以继续承担任务分发。数据库负责保存任务事实、回调 Inbox 和外部任务检查点，不需要为了 Suno 回调额外引入 Redis 队列。

## 2. 优化目标

- Suno 已生成成功时，本地能够可靠取得结果；
- Worker 重启、消息重投后继续查询原 Suno 任务，不重复提交；
- 回调重复投递不会重复处理或重复结算；
- 创建请求读取超时后不盲目重发 POST；
- 回调入口在 Suno 规定的 15 秒内返回 HTTP 200；
- 回调不可被枚举或伪造为其他任务的结果；
- 回调不可用时仍可通过低频轮询恢复。

## 3. 总体方案

```text
RabbitMQ 投递任务
        |
        v
Worker 领取任务和租约
        |
        v
后端创建一次性回调令牌
        |
        v
POST Suno generate(callBackUrl)
        |
        +---- 收到 taskId ----> 保存 provider checkpoint
        |                         |
        |                         v
        |                    回调优先 + 30 秒轮询兜底
        |
        +---- POST 读取超时 ----> 不重复 POST，等待回调

Suno POST 回调
        |
        v
Nginx -> 后端校验令牌/绑定 taskId -> Inbox 幂等入库 -> 立即 200
                                                |
                                                v
                                      Worker 读取并完成本地任务
```

正式回调地址不是一个所有任务共用的静态地址，而是每个本地任务生成独立令牌：

```text
https://wlcloudai.com/api/v1/provider-callbacks/suno/music/{64位随机令牌}
```

数据库只保存令牌的 SHA-256，不保存原始令牌。即使数据库内容泄露，也不能从哈希反推出可调用的回调 URL。

## 4. 调用时序与状态处理

### 4.1 提交前

Worker 使用当前任务的 `claimToken` 和有效租约向后端注册回调。后端创建有效期默认 24 小时的回调注册记录，返回公网 HTTPS 地址。

只有状态为 `PROCESSING`、租约未过期且 `claimToken` 一致的 Worker 可以注册或读取该任务的回调。

### 4.2 提交 Suno

Worker 将动态地址写入 Suno 请求的 `callBackUrl` 字段。

创建请求的异常分为三类：

| 异常 | 判断 | 处理方式 |
|---|---|---|
| 连接建立超时 | 请求通常尚未送达 | 可有限重试连接 |
| POST 读取超时 | Suno 可能已经收到请求 | 禁止盲目重发，转为等待回调 |
| 明确 HTTP 4xx/业务错误 | Suno 已明确拒绝 | 直接按业务失败处理 |

### 4.3 保存外部任务检查点

收到 Suno `taskId` 后，Worker 立即保存 `MUSIC_SUBMISSION` 检查点，内容包括：

```json
{
  "kind": "MUSIC_SUBMISSION",
  "provider": "suno_music",
  "model": "V5",
  "status": "SUBMITTED",
  "taskId": "Suno返回的taskId"
}
```

检查点使用版本号进行 CAS 更新。Worker 崩溃或 RabbitMQ 重新投递消息后，只要 provider、model 与检查点一致，就直接恢复查询原 `taskId`，不会重新调用生成接口。

### 4.4 等待结果

结果获取采用“双通道、同一事实源”策略：

1. 每轮先读取数据库中已经持久化的终态回调；
2. 没有回调时，再调用 Suno 详情接口；
3. 轮询间隔默认 30 秒；
4. 单次详情请求使用较短读取超时，网络错误不会立即把外部任务判定失败；
5. 默认总等待窗口为 900 秒。

只接受 `complete` 作为成功终态；`text` 和 `first` 是中间阶段；`error` 或非 200 业务码作为失败终态。

## 5. 回调接收设计

### 5.1 公网接口

```http
POST /api/v1/provider-callbacks/suno/music/{callbackToken}
Content-Type: application/json
```

成功接收后响应：

```json
{"status":"received"}
```

回调接口只执行必要操作：

1. 校验 64 位十六进制随机令牌；
2. 校验注册记录未过期；
3. 校验请求体大小不超过 256KB；
4. 读取并绑定 `data.task_id`；
5. 将完整回调写入 Inbox；
6. 提交事务并返回 HTTP 200。

音频下载、OSS 转存、计费和任务结果组装不在回调请求线程中执行。

### 5.2 幂等规则

回调 Inbox 使用以下组合唯一约束：

```text
provider_code + provider_task_id + callback_type + payload_sha256
```

相同回调重复发送时，后端捕获唯一键冲突并继续返回 200。注册记录一旦绑定 `provider_task_id`，后续使用同一令牌但携带不同任务 ID 的请求会被拒绝。

### 5.3 数据表

`provider_callback_registrations` 保存：

- 本地任务 ID；
- 路由尝试 ID；
- provider；
- 回调令牌哈希；
- 绑定后的 Suno taskId；
- 状态和过期时间。

`provider_callback_inbox` 保存：

- 回调类型和业务状态码；
- 完整 JSON；
- JSON SHA-256；
- 接收、处理时间及处理状态。

迁移文件为 `sql/112_provider_callback_inbox.sql`，正式部署脚本会按 `sql/*.sql` 文件名顺序自动执行并记录校验和。

## 6. Nginx 与正式环境配置

正式环境关键变量：

```dotenv
PUBLIC_BASE_URL=https://wlcloudai.com
PROVIDER_CALLBACK_TOKEN_TTL_HOURS=24
SUNO_POLL_INTERVAL_SECONDS=30
SUNO_TIMEOUT_SECONDS=900
```

Nginx 为 `/api/v1/provider-callbacks/` 设置独立规则：

- 最大请求体 256KB；
- 连接超时 5 秒；
- 读写超时 10 秒；
- 关闭代理缓冲；
- 转发真实 Host、来源 IP 和 HTTPS 协议信息。

公网仅放行以下精确格式的 POST 请求：

```text
/api/v1/provider-callbacks/suno/music/[a-f0-9]{64}
```

其他内部任务接口继续要求内部签名和 Worker claim token。

## 7. 发布步骤

1. 备份正式数据库；
2. 部署代码并执行 SQL 迁移；
3. 确认后端环境变量 `PUBLIC_BASE_URL=https://wlcloudai.com`；
4. 重载 Nginx 和后端服务；
5. 从公网测试回调路径的 HTTPS、请求体限制和响应耗时；
6. 启动 Worker；
7. 提交一条真实 Suno 生成任务；
8. 在 Suno 日志确认 `callBackUrl` 为 `wlcloudai.com`；
9. 在本地确认注册表、Inbox、provider checkpoint 和最终任务结果一致；
10. 重复发送同一回调，确认只产生一条 Inbox 事件且任务不重复结算。

生产验证时不要使用固定或手工构造的回调令牌，应由 Worker 通过后端注册接口取得真实地址。

## 8. 验收标准

- 正常生成任务能够通过 `complete` 回调完成；
- 同一回调投递两次，数据库只保留一个相同事件；
- Suno 创建请求发生读取超时时，不会自动再次 POST；
- Worker 在保存 `taskId` 后重启，能够恢复原任务；
- 回调暂时不可用时，30 秒轮询能取得结果；
- 非法令牌、过期令牌、不同 taskId 绑定返回拒绝；
- 回调入口处理耗时稳定低于 10 秒；
- 用户任务不再因单次 60 秒 HTTP 读取超时直接显示 `MODEL_TIMEOUT`。

## 9. 监控与告警建议

建议增加以下指标：

- `provider_callback_received_total{provider,type,code}`；
- `provider_callback_duplicate_total{provider,type}`；
- `provider_callback_latency_seconds`；
- `provider_callback_invalid_token_total`；
- `suno_submission_unknown_total`；
- `suno_poll_transport_error_total`；
- `suno_callback_recovered_total`；
- Inbox 中 `PENDING` 事件数量和最老事件年龄；
- 已存在 Suno taskId、但本地仍未终态的任务数量。

告警优先关注：回调 5xx、回调响应超过 10 秒、Inbox 长时间未消费、创建响应未知率突然升高。

## 10. 后续增强

第一阶段解决 Worker 正常运行和短时重启场景。后续应补充定时对账器：扫描已收到终态回调但本地任务尚未完成的记录，以及已保存 provider checkpoint 但超过 900 秒仍未终态的记录，重新驱动任务收敛。

对账器完成后，即使回调在 Worker 等待窗口结束后才到达，也可以自动修正本地超时状态，形成完整的最终一致性闭环。
