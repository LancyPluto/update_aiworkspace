# AI Tool Market 项目现状审计报告

审计日期：2026-06-02  
状态刷新：2026-07-01
项目阶段：MVP 后期到扩展期  
审计角色：CTPO 级技术与产品审计  

> 2026-07-01 更新：本报告保留 2026-06-02 的审计判断作为治理背景。P0 安全出库、生产启动校验、RabbitMQ 队列默认、mock/legacy 生产守卫和陈旧任务对账已经完成第一轮代码落地；剩余上线风险集中在真实密钥轮换、黄金链路验收、PPT `toolCode` 少数入口收口和用户端迁移守卫既有失败项。

## 0. 执行结论

AI Tool Market 已经不是一个简单的 AI 工具市场，而是同时承载了工具市场、任务执行、算力计费、Agent 编排、社区分发、PPT 工作台、模型配置和多模态 Worker 的复合平台。这个方向有商业想象力，但当前最大的风险不是“功能不够”，而是复杂度已经超过团队稳定交付能力。

当前阶段必须停止横向加功能，把主链路压实：用户选择工具 -> 创建任务 -> 冻结算力 -> Worker 执行 -> 结果回写 -> 结果展示 -> 社区复用 -> 再次消费。任何不能直接强化这条链路的功能，都应推迟。

## 1. 现状深度透视

### 1.1 仓库复杂度失控

- [现状描述] 仓库由 Spring Boot 后端、Vue 用户端、Next 管理端、FastAPI Agent Service、Python Worker、banana-slides 引擎、部署脚本、SQL 迁移和测试目录共同组成。只读统计显示：Java 后端主源码约 498 个文件，Agent Service 约 152 个文件，Worker 约 136 个文件，用户端约 131 个文件，管理端关键区域约 129 个文件。
- [问题本质] 这是一个多服务平台，但仍按“快速堆功能”的方式推进。模块多不等于架构成熟；如果事实源、接口边界、发布节奏和测试入口没有统一，复杂度会反过来吞掉产品速度。
- [后果预估] 每新增一个功能都会同时影响后端、用户端、管理端、Worker、Agent、SQL、文档和部署。交付速度会持续下降，线上问题定位时间会变长，团队会越来越依赖“知道历史的人”而不是系统本身。
- [具体行动建议] 立即把系统事实源收敛为三类：后端是用户、工具、任务、额度、审计事实源；Agent 只做编排和受控工具调用；Worker 只做模型执行和结果落盘。所有文档、接口和代码评审按这个边界判断。

### 1.2 单文件职责爆炸

- [现状描述] 多个核心文件已经超过正常维护阈值：`AgentRunServiceImpl.java` 1716 行、`deep_agents_engine.py` 2340 行、`AgentChatPane.vue` 2979 行、`admin-frontend/app/tools/page.tsx` 1741 行。它们都不是纯配置文件，而是承载了业务判断、状态处理、接口调用和 UI 交互。
- [问题本质] 这些文件不是“大”，是职责错误。运行编排、事件写入、额度解析、工具确认、SSE、UI 状态和错误处理混在一起，导致任何改动都要读完整上下文。
- [后果预估] 缺陷会集中在这些巨型文件里，测试很难覆盖到真正风险点。未来新增 Agent 能力、工具配置字段、社区归因或任务状态时，会不断产生隐性回归。
- [具体行动建议] P1 拆分这些文件。后端按 Run 生命周期、事件、工具确认、设置解析、状态机拆；Agent 按引擎选择、工具循环、记忆、文件上下文拆；前端按消息流、输入区、事件时间线、工具确认、附件管理拆。

### 1.3 后端、Agent、Worker 的运行时边界混乱

- [现状描述] README 声称 Spring Boot 拥有用户、会话、运行、工具、额度、持久化和审计，但代码与配置里 Agent Service 和 Worker 也都保留模型配置、默认 token、工具执行策略、超时、轮询、记忆或上下文字段。
- [问题本质] 当前边界是“口头上后端是事实源，代码里各服务都有兜底”。兜底本身不是错，但没有强制失效条件时，兜底会变成第二套事实源。
- [后果预估] 一旦后端配置、Agent 默认值、Worker 默认值不一致，会出现额度扣费不准、工具路由不准、任务状态不准、模型调用成本不可审计的问题。这会直接伤害商业化，因为计费和稳定性是用户信任底线。
- [具体行动建议] 明确三条硬规则：Agent 不直接拥有额度结算；Worker 不自行推导工具业务规则；所有任务状态和扣费以 Spring Boot 内部接口回写为准。Agent/Worker 的默认配置只能用于本地开发，生产环境必须拒绝启动。
- [2026-07-01 更新] Agent Service 与 Worker 已补生产启动校验；默认内部 token、占位模型 key、mock provider 在生产环境会阻止启动。

### 1.4 旧接口和兼容逻辑继续占用团队注意力

- [现状描述] 项目同时存在 `/api/v1/tools` 与旧 `/api/v1/ai-tools`、`/api/admin/v1/tools` 与旧 `/api/admin/ai-tools`。PPT 仍保留 legacy `ppt-workflow` marker、单 PPT 工具兜底和缺 `toolCode` 的迁移期兼容。
- [问题本质] 这些不是“兼容友好”，而是没有退场机制。旧接口继续可用，会让前端、测试、文档和运营配置同时支持两套模型。
- [后果预估] 数据迁移永远迁不完，配置导入导出会变得不可控，管理端会继续出现“新旧字段都能改但不知道哪个生效”的状态。
- [具体行动建议] 立刻建立废弃清单：旧 ai-tools 接口、PPT legacy marker、单 PPT 工具兜底、缺 `toolCode` 的 PPT 创建都标记为 P0/P1 移除对象。先加日志和后台提示，再在 2 个迭代内删除调用路径。
- [2026-07-01 更新] 旧 `ai-tools` 后端兼容接口已加废弃日志；PPT 工作流新写入改为 `tool-integration`，旧 `ppt-workflow` 仅保留读取兼容。缺 `toolCode` 的少数入口仍需后续收口。

### 1.5 安全边界存在生产级风险

- [原始现状描述] `.env`、`WXcert/*.pem`、`_remote.py`、`_fix_remote.py` 已被 git 跟踪；`.env` 当前还有本地修改。后端有生产模式默认密钥校验，但 Agent Service 和 Worker 仍保留 `local-internal-token`、`replace-with-model-key` 等默认值。管理端开发模式可通过 mock 绕过登录，mock 支付入口在公共路径规则中存在。
- [问题本质] 支付证书、远程部署凭据、内部接口 token、模型 key 和 mock 入口属于同一类信任边界。它们不能靠“开发人员记得不要开生产模式”来保护。
- [后果预估] 最坏结果是支付证书泄露、内部任务接口被伪造、算力被盗刷、用户资产被越权访问。即使没有真实泄露，投资人或客户尽调也会把这判定为严重工程治理缺陷。
- [具体行动建议] P0 处理：真实 `.env` 和证书出库，改为 `.env.example` + 密钥管理；Agent/Worker 增加生产启动校验；mock 支付和 mock 登录只允许显式本地环境；内部接口强制签名并在所有服务统一校验默认 token。
- [2026-07-01 更新] 敏感文件已从 Git 索引移除并加入忽略规则，Agent/Worker 生产默认值校验已补齐，管理端 mock 登录和用户端 mock 数据已限制为显式开发开关。上线前仍必须人工轮换所有可能暴露过的密钥和证书。

### 1.6 SQL 迁移治理混乱

- [现状描述] `sql` 目录下存在同编号迁移脚本，例如 `005`、`006`、`007`、`012`、`013`、`014`、`015`、`021`、`024`、`025`、`035`、`036` 等编号重复。初始化、seed、修复脚本混在一个线性目录里。
- [问题本质] 数据库迁移没有单一顺序事实源。脚本名看似有序，实际无法稳定表达“哪个先执行、哪个只执行一次、哪个只用于修复”。
- [后果预估] 本地库、测试库、生产库会出现结构漂移。某个环境能跑不代表另一个环境能跑，最终会卡在上线窗口。
- [具体行动建议] 建立迁移规则：schema migration、seed、repair 分目录；编号全局唯一；每个脚本声明适用环境和幂等性；测试 schema 与生产 migration 同步生成或定期校验。

### 1.7 队列事实源不稳定

- [原始现状描述] README 推荐任务队列闭环，后端配置默认 `TASK_QUEUE_BACKEND:rabbitmq`，Worker 默认 `task_queue_backend: redis`，项目同时保留 Redis consumer 和 RabbitMQ consumer。
- [问题本质] 队列双轨不是问题，问题是没有明确默认生产轨道。任务系统必须有一个强事实源，否则重试、死信、幂等、冻结额度释放都会被拆散。
- [后果预估] 任务丢失、重复执行、死信不可恢复、额度冻结无法对账。这些问题都会直接影响付费转化和客服成本。
- [具体行动建议] P0 确认 RabbitMQ 为生产任务队列，Redis 仅保留本地或兼容入口；后端、Worker、部署和 README 默认值统一；死信重放和幂等测试必须作为上线门槛。
- [2026-07-01 更新] Worker 默认队列已改为 RabbitMQ，生产环境显式配置 Redis 队列会启动失败；Worker 启动日志会输出队列、死信队列、重试延迟和最大重试次数。

### 1.8 测试覆盖看起来多，但风险覆盖不均衡

- [现状描述] 后端测试覆盖较多，Agent Service 测试较多，Worker 测试相对少；前端主要依赖 build 和少量 e2e。巨型页面和巨型服务没有与其复杂度匹配的分层测试。
- [问题本质] 当前测试更像“功能点验收”，不是“系统风险验收”。计费、任务状态、Agent 工具调用、Worker 回调、社区归因这些跨服务链路仍需要端到端基线。
- [后果预估] 单测通过但真实链路失败。用户看到的是任务卡住、扣费异常、结果不展示、同款创作不归因。
- [具体行动建议] P1 建立 5 条黄金链路测试：文本任务、图片任务、视频任务、Agent 调用工具、社区同款创作并产生消费。每条链路都必须覆盖冻结、执行、回写、展示、扣费或释放。

## 2. 产品逻辑挑战

### 2.1 功能数量已经超过当前商业验证所需

- [现状描述] 项目同时推进工具市场、Agent 首页、传统 Chat、Dashboard、素材库、社区、灵感收藏、公开主页、PPT 工作台、充值计费、管理后台模型配置、工作流画布和社区运营。
- [问题本质] 这不是产品丰富，这是验证目标分裂。早期平台最该验证的是“用户愿不愿意为稳定生成和复用付费”，不是“平台能不能像成熟社区和成熟 Agent 产品一样什么都有”。
- [后果预估] 用户入口会混乱，团队会把时间花在低频功能上，核心工具生成体验反而不稳定。商业转化会被功能噪音稀释。
- [具体行动建议] 下一阶段只押三条路径：工具任务消费、Agent 受控调用工具、社区同款回流消费。评论、关注、私信、复杂推荐、独立专题 CMS、音乐生成一律停。

### 2.2 社区方向正确，但不能提前做泛社区

- [现状描述] 社区文档已经明确不做评论、关注、私信和复杂推荐，这是正确判断。当前社区核心链路是作品发现 -> Prompt 学习 -> 同款创作 -> 回到工作台。
- [问题本质] 社区的商业价值不是社交，而是降低用户创作门槛并带来二次消费。泛社区能力会引入审核、举报、治理和推荐成本。
- [后果预估] 如果过早做社交，团队会进入内容治理泥潭，主链路消费增长没有提升，运营成本先上升。
- [具体行动建议] 社区只做案例发现、Prompt 可见性、同款创作、工具案例入口、归因事件。所有社交互动只保留点赞、收藏、同款计数。

### 2.3 Agent 能力需要降噪

- [现状描述] Agent Service 支持 LangGraph、Deep Agents、记忆、文件解析、工具调用、路由调试、模型选择、上下文窗口和后台参数管理。
- [问题本质] Agent 的核心价值不是“看起来智能”，而是把用户意图稳定转成平台工具消费。如果 Agent 不能稳定调用可计费工具，它就是高成本聊天入口。
- [后果预估] 模型成本上升，任务成功率不稳定，用户把 Agent 当聊天玩具而不是生产工具。
- [具体行动建议] Agent 下一阶段只优化三件事：工具识别准确率、缺参追问质量、工具执行可审计。长期记忆、Deep Agents 和复杂子代理先做稳定性保护，不扩功能。

### 2.4 管理后台过度承载

- [现状描述] 管理端同时管理工具、模型、Prompt、工作流、计费、用户、社区、Agent runs、记忆、运行参数和配置导入导出。
- [问题本质] 管理后台已经不是“后台”，而是半个低代码平台。没有信息架构分层时，运营人员会被配置项淹没。
- [后果预估] 配置错误概率上升，工具上线依赖技术人员，业务无法自助运营。
- [具体行动建议] P2 重构管理端信息架构：运营日常、模型与成本、工具配置、运行诊断、系统设置分区。高风险配置必须有预览、测试和回滚。

## 3. 立即停产清单

以下内容当前应停止新增开发，除非先完成 P0 稳定性整改：

- 评论、关注、私信、关注流、复杂推荐算法。
- 独立专题 CMS 和复杂社区运营能力。
- 音乐生成、新模型族扩展、新多模态大功能。
- 新增工作流画布能力。
- 新增旧 ai-tools 接口兼容。
- 新增 PPT legacy `ppt-workflow` marker 兼容。
- 新增 mock 支付或 mock 管理登录路径。
- 新增没有端到端验收的 Agent 工具能力。

## 4. 核心重构计划

20% 的关键改动能换来 80% 稳定性提升：

1. 密钥和证书出库，生产默认值强校验扩展到后端、Agent、Worker。
2. 统一任务队列事实源，生产默认 RabbitMQ，Redis 只做兼容或本地。
3. 固化任务/额度状态机，覆盖冻结、执行、成功扣费、失败释放、超时对账、死信重放。
4. 清理旧接口和迁移兜底，减少双轨配置。
5. 拆分巨型服务和巨型页面，让核心链路变得可测试。
6. 建立黄金链路验收，确保任务消费、Agent 工具调用、社区同款回流可以持续回归。

## 5. 审计结论

AI Tool Market 的问题不是没有产品方向，而是方向太多、边界太松、兼容太久、安全治理太晚。下一阶段不要再证明“还能加功能”，要证明“核心链路能稳定赚钱”。这就是当前项目的技术产品优先级。
