# AIGC 商业上线问题修复推进计划（代码层级，2026-07-10）

## 1. 文档目标

本文把 2026-07-10 上线审查中发现的问题拆成可执行的代码任务、模块边界、依赖顺序和验收门禁。

本轮排序遵循以下原则：

1. 先统一测试、路由、数据和发布契约，减少多人并行开发时的重复沟通。
2. 再补 AIGC 合规、灾备、支付运营等跨模块能力。
3. 凭据轮换、默认口令、密钥出库和 Git 历史清理统一放在最后一个阶段实施，避免开发期间反复改环境变量、部署账号和联调凭据。
4. 凭据治理虽然最后实施，但仍是正式扩大公网流量前的强制门禁；在该阶段完成前，只允许受控内测。

本文不替代以下文档：

- `商业上线P0发布门禁-2026-06-30.md`：最终发布检查清单。
- `生产化可靠性补齐方案-2026-07-09.md`：登录态、任务租约、失败成本和监控的既有设计。
- `qianduan-user-web-route-map.md`：用户端迁移路由事实源。

## 2. 当前基线

### 2.1 已具备的基础

- 任务执行已有 RabbitMQ、claim/lease、Worker 回调幂等和失败释放算力。
- 微信、支付宝支付回调已有验签、商户校验、金额校验和外部交易号冲突检查。
- Agent Service 全量测试 383 项通过，Worker 全量测试 189 项通过。
- 用户端和管理端生产构建可以通过，管理端 TypeScript 类型检查可以通过。
- Prometheus、Grafana、Loki 和业务指标已有最小框架。

### 2.2 当前不通过项

- 后端全量测试 353 项中有 1 项中文初始化数据乱码失败。
- 用户端 `npm test` 有路由迁移、缺失页面、乱码守卫和模块别名加载等既有失败。
- 管理端 Node 测试有失败，`npm run lint` 因未安装 ESLint 无法执行。
- CI 前端任务只执行构建，没有执行用户端测试、管理端测试、类型检查和 lint。
- 生产部署健康检查不会因服务异常而失败，也没有自动回滚。
- 用户端生产依赖审计存在 DOMPurify 中危项，管理端存在 Next.js 高危项和 PostCSS 中危项。
- 生产落地页 Logo 资源缺失，法律、联系、状态等入口仍是占位链接。
- 没有完整数据库备份、恢复演练、退款、发票和支付日终对账体系。
- 没有平台层 AIGC 显式标识、文件元数据隐式标识和统一内容审核链路。

## 3. 推进顺序总览

| 阶段 | 主题 | 主要负责人 | 跨团队依赖 | 建议合并条件 |
| --- | --- | --- | --- | --- |
| 0 | 测试与 CI 基线收口 | 各模块开发 + CI 维护者 | 低 | 所有既有门禁可稳定执行 |
| 1 | 用户端路由与商业首屏收口 | User Web | 低 | 路由契约、Logo、法律入口可用 |
| 2 | AIGC 标识与内容治理 | Backend + Worker + User Web + Admin | 高 | 生成、存储、展示、下载全链路有审计记录 |
| 3 | 数据、迁移、发布与灾备 | Backend + DevOps | 中 | 可备份、可恢复、发布失败可停止或回滚 |
| 4 | 支付运营与运行时加固 | Backend + Admin + DevOps | 中 | 对账、退款、依赖漏洞和响应头收口 |
| 5 | 凭据、口令与密钥治理 | DevOps + Backend + 安全负责人 | 高但集中 | 单次维护窗口完成切换和验证 |

阶段 0 是所有后续工作的共同前置。阶段 1 完成后，阶段 2、阶段 3 可以并行；阶段 4 依赖阶段 3 的迁移和备份约定；阶段 5 必须在前述代码结构稳定后统一实施。

## 6. 阶段 2：AIGC 标识与内容治理

目标：建立“输入审核、供应商生成、输出审核、标识、存储、展示、下载、社区发布”的完整链路。该阶段是唯一需要 Backend、Worker、User Web、Admin 四方共同对齐的阶段，因此先定义接口和状态机，再并行写代码。

### C-01 统一状态和审计模型

建议新增：

- `generated_content_compliance_records`
  - `task_id`
  - `asset_id`
  - `content_type`
  - `precheck_status`
  - `postcheck_status`
  - `label_status`
  - `provider`
  - `provider_request_id`
  - `review_status`
  - `review_reason`
  - `created_at` / `updated_at`
- `ai_tasks` 或任务详情响应增加只读合规摘要，避免前端直接拼审计表。

状态建议：

- 审核：`PENDING`、`PASSED`、`BLOCKED`、`MANUAL_REVIEW`、`FAILED`。
- 标识：`PENDING`、`APPLIED`、`NOT_APPLICABLE`、`FAILED`。

首个 PR 只包含 SQL、DTO、状态枚举、OpenAPI 和空实现，不同时接入所有供应商。

### C-02 生成前和生成后审核

Backend：

- 新增 `com.aiminilab.aitoolmarket.compliance` 模块。
- 定义 `ContentModerationService` 接口，屏蔽具体审核供应商。
- 任务创建前检查文本和用户上传素材；高风险结果不进入队列。
- Worker 回传结果后，在任务成功结算前完成输出审核或进入人工复核状态。
- 社区发布只允许 `postcheck_status=PASSED` 的资产。

Worker：

- 统一映射供应商 safety rejection，保留供应商 request id 和错误码。
- 原始未审核媒体只写私有存储，审核和标识完成后再生成可下载版本。
- 不把供应商“调用成功”等同于平台“任务可交付成功”。

Admin：

- 增加人工复核队列、原因、处理人、处理时间和审计日志。
- 支持放行、拦截、下架，不直接删除计费和任务事实记录。

### C-03 显式和隐式标识

Worker 建议新增：

- `worker/utils/aigc_labeling.py`
- 图片：显式标识层 + 文件元数据。
- 视频：画面显式标识 + 容器元数据。
- 音频：播放/下载页面显式提示 + 文件元数据。
- 文本、报告：页面标识；导出文件中写入标识说明和元数据。

Backend：

- 只向用户端返回已通过审核且完成标识的交付资产 URL。
- 保留原始资产、审核资产、交付资产之间的关联和访问权限。
- 下载接口记录标识版本，便于后续规则调整和追溯。

User Web：

- 结果卡片、资产预览、社区作品和下载确认中统一展示“AI 生成”标识。
- 禁止前端通过替换 URL 绕过交付资产接口下载原始文件。

### C-04 投诉举报和处置闭环

现有社区举报能力继续复用，但需要补齐：

- 公共投诉入口和处理时限说明。
- 举报与生成任务、资产、用户、审核记录的关联。
- 管理端处理结果反馈。
- 违法内容停止展示、停止下载、限制账号和留存处置记录。

验收场景：

1. 正常文本、图片、视频生成后均有合规记录和标识版本。
2. 输入被拦截时不调用供应商、不冻结或及时释放算力。
3. 输出被拦截时不公开原始媒体，用户扣费策略与失败成本记录一致。
4. 下载文件包含规定的显式/隐式标识。
5. 未通过审核的资产无法发布到社区。

## 7. 阶段 3：数据、迁移、发布与灾备

目标：保证任何一次代码或 SQL 发布失败后，系统仍可恢复，余额、订单、任务和配置数据不会因单机故障永久丢失。

### R-01 数据库备份与恢复演练

建议新增：

- `deploy/scripts/backup_mysql.sh`
- `deploy/scripts/restore_mysql_to_staging.sh`
- `deploy/backup/README.md`

实施内容：

- 每日全量备份 + binlog 连续归档，备份文件加密后写入独立 OSS bucket。
- 设置保留周期、失败告警和校验和。
- 每月至少自动恢复到隔离数据库一次，并执行用户、订单、余额和任务抽样校验。
- 在正式引入退款前，先确定账本表和订单表的 RPO/RTO。

### R-02 SQL 迁移脚本加固

短期不同时引入 Flyway，先降低现有迁移机制的风险：

- `_sql_migration_log` 增加 checksum 和执行耗时。
- 已执行文件 checksum 变化时直接失败。
- 禁止因某一个 `Duplicate column/key` 就把整个多语句 SQL 文件标记成功。
- `mysql_q` 不再对写操作使用 `|| true` 吞错。
- 每个新 SQL 文件尽量保持单一职责和可重放性。
- SQL、`DataInitializer`、测试 schema 三份结构在同一个 PR 更新，并增加 schema 一致性测试。

涉及文件：

- `deploy/scripts/apply_sql_migrations.sh`
- `backend/src/main/java/com/aiminilab/aitoolmarket/config/DataInitializer.java`
- `backend/src/test/resources/schema-test.sql`
- `sql/*.sql`

中期再单独评估 Flyway；不要把迁移工具替换和业务表改造放进同一个 PR。

### R-03 服务健康检查和发布失败门禁

涉及文件：

- `deploy/docker-compose.yml`
- `deploy/docker-compose.nginx.yml`
- `deploy/scripts/ci_remote_deploy_light.sh`
- `.github/workflows/dev-delivery.yml`

实施内容：

- Backend、Agent Service、Worker 增加真实 healthcheck。
- Worker 健康检查至少包含进程存活、RabbitMQ 连接和最近一次心跳。
- 发布脚本等待所有本次变更服务健康；超时必须非零退出。
- 删除关键 smoke check 后的 `|| true`。
- 外部 smoke check 对非 2xx/3xx 明确失败，不只判断能否建立连接。
- 保存上一版本镜像 tag 和 commit，应用健康失败时自动恢复上一版本。
- 数据库迁移先备份；若迁移不可逆，发布说明必须明确旧版本是否兼容新 schema。

### R-04 告警和容量保护

实施内容：

- 增加 Alertmanager 或等价告警出口。
- 最低告警：登录失败突增、支付回调失败、主队列积压、死信增长、任务成功率、冻结算力超时、供应商失败成本、磁盘空间、MySQL 备份失败。
- Compose 增加日志轮转、CPU/内存限制和磁盘水位保护。
- Grafana 保留登录认证，不作为匿名公共页面。

验收：

- 在 staging 人为让 Backend 启动失败，部署必须失败且恢复上一版本。
- 从备份恢复后，抽样用户余额、充值订单、任务和计费日志一致。
- 制造一条死信和一次支付回调失败，值班渠道能收到告警。

## 8. 阶段 4：支付运营与运行时加固

实施约束：

- 退款不能直接覆盖历史充值日志，必须新增反向账本记录。
- 明确可退款余额、已消费余额、赠送算力和礼品卡的处理规则。
- 所有退款请求必须有幂等键、操作人和审计日志。
- 第一版可只支持后台人工发起，不急于开放用户自助退款。

### P-03 发票和售后入口

- 第一版建立发票申请记录、抬头、金额、订单关联和处理状态。
- 用户端提供可找到的售后与退款规则入口。
- 管理端可以导出订单、退款和发票申请，避免依赖人工查数据库。

### H-01 依赖漏洞升级

- 管理端升级 Next.js 到已修复审计漏洞的稳定版本，并回归代理、登录 Cookie、上传和 `/admin` basePath。
- 用户端升级 DOMPurify，并回归 Markdown、富文本、任务结果和社区内容渲染。
- 升级 PostCSS 后重新构建两端 CSS。
- 完成升级后，将 Node、Python、Maven 安全审计改为 CI 阻断项。

### H-02 浏览器安全响应头

在 Nginx 统一增加并验证：

- `Strict-Transport-Security`
- `Content-Security-Policy`，先 report-only 再强制
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy`
- `Permissions-Policy`
- 合理的 `frame-ancestors` 或 `X-Frame-Options`

要求：用户端、管理端、支付跳转、OSS/CDN 图片和 Grafana 子路径均通过浏览器回归后再启用强制 CSP。

## 9. 阶段 5：凭据、口令与密钥治理（最后实施）

目标：前面阶段先完成代码承载能力，本阶段再用一次受控维护窗口完成全部凭据切换，避免开发过程中多次轮换导致环境和人员反复对齐。

### 执行前置条件

- 阶段 0 至阶段 4 已合并并通过 staging 验收。
- 生产 Compose 已支持无默认值、缺少变量即启动失败。
- 管理员初始化、登录限流、密钥加密落库和部署 SSH key 路径已完成代码开发。
- 已准备回滚凭据，但不继续使用已经入库的旧凭据。

### S-01 生产配置默认拒绝启动

涉及文件：

- `deploy/docker-compose.yml`，拆出明确的 production override
- `.env.example`
- Backend、Worker、Agent Service 的 startup validator

实施内容：

- 生产环境不允许 MySQL、RabbitMQ、Grafana、JWT、内部 Token 使用默认值。
- `APP_ENV` 和 `APP_PRODUCTION_MODE` 统一为一个事实源，Cookie Secure、验证码 debug code 和启动校验使用同一判断。
- Agent 内部签名校验在生产强制开启。

### S-02 模型密钥和控制台 Cookie 加密落库

涉及文件：

- `ModelVendorAccountMapper`
- `AgentModelConfigMapper`
- 凭据解析 Service
- 配置包导入导出

实施内容：

- 引入独立主密钥或 KMS，数据库只保存密文和 key version。
- API 返回继续只提供掩码，不允许导出明文。
- 支持旧明文记录在线迁移，迁移完成后拒绝继续写入明文。
- 主密钥不得与数据库、代码仓库或配置导出包放在同一位置。

### S-03 管理员账号安全

- 删除 `DataInitializer` 中固定 `admin/123456` 初始化逻辑。
- 首次部署通过一次性初始化命令生成管理员，输出一次性随机密码或使用受控身份源。
- 管理员首次登录强制改密，增加登录限流、失败锁定、审计告警；优先补 MFA。
- README 和所有运维脚本不得再提供默认生产管理员密码。

### S-04 Git 出库和历史清理

- 从 Git 索引移除 TLS 私钥、微信支付私钥和包含生产密码的诊断脚本。
- `.gitignore` 增加站点私钥、支付证书和本地生产诊断脚本规则。
- 使用历史清理工具移除已泄露内容；团队重新拉取或重置受影响分支。
- CI 增加 secret scanner 和提交前检查。

### S-05 单次维护窗口轮换

建议轮换顺序：

1. 创建新的部署 SSH key 和最小权限部署用户，验证新通道。
2. 轮换数据库、RabbitMQ、Grafana、对象存储和模型供应商凭据。
3. 轮换 JWT secret、内部 API token，并使旧会话失效。
4. 重新签发站点 TLS 证书和微信支付相关证书/密钥。
5. 更新 GitHub Secrets、生产密钥存储和监控探针。
6. 重启服务并执行登录、支付、生成、回调、下载和监控黄金链路。
7. 撤销旧凭据，确认旧凭据不能再登录或调用。

本阶段验收必须由两人复核：实施人和复核人分别记录新凭据生效、旧凭据失效和服务恢复时间；文档只记录凭据版本和轮换时间，不记录明文。

## 10. PR 和代码所有权建议

为减少开发间对齐成本，每个 PR 只解决一个契约面：

| PR | 变更范围 | 不应混入 |
| --- | --- | --- |
| PR-01 | 后端编码、用户端测试、管理端 lint/test、CI 门禁 | 业务功能和 UI 改版 |
| PR-02 | 用户路由、Logo、法律路由和落地页 | AIGC 审核后端 |
| PR-03 | 合规 SQL、状态枚举、DTO、OpenAPI | 具体供应商审核实现 |
| PR-04 | Backend/Worker 审核与标识链路 | 支付和部署脚本 |
| PR-05 | User Web/Admin 合规展示与复核 | 路由大迁移 |
| PR-06 | 备份、迁移脚本、schema 一致性 | 凭据轮换 |
| PR-07 | 健康检查、发布回滚、告警 | 业务表结构改造 |
| PR-08 | 支付对账、退款、发票 | 前端视觉重构 |
| PR-09 | 依赖升级和安全响应头 | 密钥历史清理 |
| PR-10 | 凭据加密、管理员安全、出库和轮换 | 其他业务开发 |

协作规则：

- 所有 PR 从最新 `dev` 创建，合并前重新同步 `dev`。
- 修改 SQL 时，同 PR 更新 SQL、`DataInitializer`、测试 schema 和迁移说明。
- 修改路由时，同 PR 更新 route helper、导航、迁移守卫和路由文档。
- 修改内部 API 时，同 PR 更新 Backend、Worker/Agent client、签名测试和 OpenAPI。
- 不在问题修复 PR 中顺带拆巨型页面或重写框架；结构重构另开 PR。
