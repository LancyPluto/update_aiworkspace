# AI Tool Market 错误码设计规范

> 文档版本：1.0
>
> 代码基线：`feature/test-docs` @ `4d18f7f46229`，2026-07-27
>
> 适用范围：Backend、Worker、Agent Service、用户端、管理端、数据库、日志与监控
>
> 规范状态：当前实现基线与后续扩展的强制约束

实现状态说明：第 5、6 节是当前代码事实；其余章节同时包含强制目标规则。凡现有实现尚未满足规则的地方，本文均以“当前缺口”明确标注，不应把目标规则误读为已经全链路落地。

## 1. 目的与适用范围

本文统一规定平台错误码的定义、HTTP 映射、响应字段、异常类型、跨服务传输、持久化、脱敏、可观测性、兼容迁移和扩展流程。

当前代码中存在三类看起来都像“错误码”的值，必须严格区分：

1. **正式应用错误码（canonical error code）**：由 `ErrorDefinitionRegistry` 注册，格式为“业务模块 + 三位序号”，是新开发唯一允许对外返回和写入新失败数据的 `errorCode`。
2. **LEGACY API 错误码**：`ErrorCode` 枚举中的旧字符串，用于滚动升级期间兼容旧 `ApiResponse`，禁止作为新设计继续扩展。
3. **运行时兼容码**：Worker、Agent、Workflow 历史链路中的裸字符串或动态拼接值。它们只可作为待迁移别名或内部 `failureReason`，不得作为新公开契约的示例。

本文使用以下规范词：

- **必须**：不满足即不得合并或发布。
- **应该**：原则上必须满足，偏离时需在评审中说明原因和补偿措施。
- **禁止**：不得新增；历史用法仅可在明确的兼容边界内保留。

## 2. 唯一真源与术语

### 2.1 唯一真源

`backend/src/main/java/com/aiminilab/aitoolmarket/common/error/ErrorDefinitionRegistry.java` 是正式应用错误码的唯一真源。当前注册 **51 个**正式码。

Registry 之外的字符串，即使名为 `errorCode`，也不是正式应用错误码。跨服务入口收到非 Registry 值时，必须先执行别名归一或降级，禁止原样扩散到新的响应、任务、运行记录和监控标签。

### 2.2 字段边界

| 字段 | 所有者 | 用途 | 是否可返回用户端 |
|---|---|---|---|
| `errorCode` | 平台 | 稳定、低基数、可统计的失败语义 | 是 |
| `userMessage` | 平台 | 简短、受控、可直接展示的用户文案 | 是 |
| `developerMessage` | 平台 | 已脱敏的开发与运维诊断 | 否，仅认证管理员或验签内部调用 |
| `failureReason` | 平台内部 | 熔断、路由、状态机等细分机器原因 | 否 |
| `providerErrorCode` | 外部供应商 | 供应商原始错误标识，可能变化且不可控 | 否 |
| `providerRequestId` | 外部供应商 | 向供应商追查请求的标识 | 否 |
| `traceId` / `failureTraceId` | 平台 | 跨服务日志和失败记录关联 | 是，且不含敏感信息 |
| `errorMessage` | 历史字段 | LEGACY 壳及任务/运行失败快照的兼容字段 | V2 顶层错误壳禁止；领域 `data` 中仍有待退场兼容字段 |

`failureStage`、`deliveryState`、`retryScope` 是执行元数据，不是 `errorCode`，不得注册为错误码。

`failureReason` 在本文中表示应从公开错误码中拆出的内部逻辑字段；当前并非所有服务和数据表都已落地该列。迁移完成前，现有裸字符串只能在明确的兼容分支中使用，不能据此宣称已经实现统一 `failureReason` 契约。

## 3. API 响应契约

### 3.1 V2 标准 JSON API 成功响应

V2 标准 JSON API 成功 envelope 只允许 `code`、`data`、`traceId`：

```json
{
  "code": "SUCCESS",
  "data": {
    "taskId": 12345
  },
  "traceId": "d934b747-62bd-4bfa-a474-9e718db8ef8e"
}
```

SSE、文件下载、流式媒体、健康探测和必须原样响应的外部回调不套用该成功 envelope，按各自 `Content-Type` 与接口契约返回；它们的失败路径仍不得泄漏任意内部诊断。

### 3.2 V2 用户错误响应

用户端错误只允许 `errorCode`、`userMessage`、`traceId`：

```json
{
  "errorCode": "CREDIT_001",
  "userMessage": "可用算力不足",
  "traceId": "d934b747-62bd-4bfa-a474-9e718db8ef8e"
}
```

### 3.3 V2 管理与可信内部错误响应

已认证管理员或已验签内部调用只允许 `errorCode`、`developerMessage`、`traceId`：

```json
{
  "errorCode": "CREDIT_001",
  "developerMessage": "Credit check rejected; availableCredits=2; requiredCredits=20; operation=task.create",
  "traceId": "d934b747-62bd-4bfa-a474-9e718db8ef8e"
}
```

### 3.4 可见性规则

| 调用方 | 响应壳 | 判定条件 |
|---|---|---|
| 普通用户、匿名调用 | 用户错误壳 | 默认行为 |
| 管理登录接口 | 用户错误壳 | 即使路径属于管理端，也不得回传诊断 |
| 已认证管理员 | 管理错误壳 | 管理路径且 `AuthContext` 中用户类型为 `ADMIN` |
| 内部服务 | 管理错误壳 | `/api/internal/v1/**` 且内部签名验证成功 |
| 未认证管理请求、未验签内部请求 | 用户错误壳 | 仅有 URL 前缀不构成信任 |

V2 **标准顶层错误 envelope** 有以下硬性字段约束：

- 禁止 `message`。
- 禁止 `data`，包括 `data: null`。
- 禁止 `details`。
- 禁止同时出现 `userMessage` 和 `developerMessage`。
- 禁止把数据库根因、SQL、堆栈、服务器路径、供应商原始正文或密钥放入任一响应。

### 3.5 LEGACY 响应

当前默认配置仍为 `APP_ERROR_CONTRACT_MODE=LEGACY`。LEGACY 响应保留旧结构：

```json
{
  "code": "CREDIT_NOT_ENOUGH",
  "message": "可用算力不足",
  "data": null,
  "traceId": "d934b747-62bd-4bfa-a474-9e718db8ef8e"
}
```

LEGACY 只用于滚动升级兼容。新接口、前端和跨服务客户端必须能读取 V2；不得因为生产默认仍为 LEGACY 而继续新增旧壳字段。

在 LEGACY 模式下，历史 `BusinessException` 仍可能为兼容旧客户端统一返回 HTTP `400`；V2 才使用正式定义中的 `httpStatus`。调用方不得从 LEGACY HTTP 状态反推完整业务语义。

### 3.6 任务与运行失败快照

Task、Workflow、Agent 的详情接口可能以 HTTP 成功响应返回领域资源，并在 `data` 中携带该资源的失败快照。这类 `data.errorCode`、`data.userMessage`、`data.developerMessage` 或兼容 `data.errorMessage` 不属于第 3.2、3.3 节的顶层错误 envelope，但仍必须遵守投影隔离：

- 普通用户资源投影只能包含正式 `errorCode`、安全 `userMessage` 和可公开 TraceId。
- 管理员资源投影可以包含已脱敏 `developerMessage`、供应商诊断标识和失败 TraceId。
- 禁止在普通用户投影中回传 `developerMessage`、旧任意 `errorMessage` 或供应商原始正文。
- 现有领域 `errorMessage` 仅作滚动兼容，消费者迁移完成后应按前向版本计划退场；不得在新 DTO 中复制该字段。

## 4. 正式错误定义模型

每个正式码必须实现 `ErrorDefinition`，并完整定义以下元数据：

| 元数据 | 规则 |
|---|---|
| `code` | 全局唯一且符合三位序号格式 |
| `httpStatus` | 独立表达 HTTP 传输语义，不从错误码序号推导 |
| `defaultUserMessage` | 非空、简短、受控、无敏感诊断 |
| `category` | 责任归属分类 |
| `logLevel` | 该失败默认记录级别 |
| `retryable` | 同一幂等操作能否安全重试 |

### 4.1 命名格式

正式码必须匹配：

```text
^[A-Z][A-Z0-9]*_[0-9]{3}$
```

合法示例：`API_001`、`MODEL_004`、`PPT_005`。

非法示例：

| 错误写法 | 原因 |
|---|---|
| `model_004` | 只能使用大写字母和数字 |
| `MODEL_04` | 序号必须固定三位 |
| `MODEL_TIMEOUT` | 使用语义单词代替稳定序号 |
| `MODEL_API_001` | 模块前缀中出现额外下划线 |
| `HTTP_500` | 把 HTTP 状态混入业务码 |
| `TASK_FAILED` | 以运行状态动态拼码 |

三位数字只是模块内的永久稳定序号，不承载 HTTP 状态、严重程度、可重试性、版本或时间含义。

### 4.2 模块前缀

当前已使用前缀：

| 前缀 | 责任边界 | 当前范围 |
|---|---|---|
| `API` | 通用请求解析、参数、资源和媒体类型 | `API_001`～`API_006` |
| `AUTH` | 登录凭据与访问授权 | `AUTH_001`～`AUTH_003` |
| `TOOL` | 工具资源与工具状态 | `TOOL_001`～`TOOL_002` |
| `TASK` | 通用任务资源、状态和幂等 | `TASK_001`～`TASK_003` |
| `MODEL` | 模型供应商依赖与模型安全拒绝 | `MODEL_001`～`MODEL_005` |
| `PAY` | 支付依赖、回调和支付配置 | `PAY_001`～`PAY_005` |
| `SYSTEM` | 本系统未分类内部故障 | `SYSTEM_001` |
| `WORKFLOW` | 工作流业务与执行 | `WORKFLOW_001` |
| `CREDIT` | 平台算力余额 | `CREDIT_001` |
| `MEMBER` | 会员权益与订单状态 | `MEMBER_001`～`MEMBER_002` |
| `AGENT` | Agent 会话、运行、配额和安全 | `AGENT_001`～`AGENT_016` |
| `SESSION` | 非 Agent 的通用会话资源 | `SESSION_001` |
| `PPT` | PPT 项目、步骤、依赖和执行 | `PPT_001`～`PPT_005` |

新增前缀必须对应有明确所有者的稳定业务边界。禁止按接口、HTTP 状态、供应商、团队名、版本或单次项目创建前缀。选择下一编号前必须同时检查当前 Registry、本文档和 Git 历史；“当前最大值 + 1”只是候选，不代表可以跳过历史占用检查。

### 4.3 Category

`category` 只能取：

| Category | 适用场景 |
|---|---|
| `VALIDATION` | 请求无法解析、格式或字段不合法，以及通用 API 路由或资源定位失败 |
| `AUTHENTICATION` | 未登录、凭据缺失或过期 |
| `AUTHORIZATION` | 已识别调用方但无权访问，或平台自身的访问安全策略拒绝 |
| `BUSINESS` | 可预期的业务规则、状态或额度冲突 |
| `DEPENDENCY` | 模型、支付等外部依赖失败 |
| `SYSTEM` | 平台自身配置、存储或未知内部故障 |

Category 按责任归属选择，不按 HTTP 状态选择。同为 `503` 的错误可以分别属于 `DEPENDENCY` 或 `SYSTEM`。

模型供应商执行的内容安全拒绝属于依赖边界，当前 `MODEL_005` 因此使用 `DEPENDENCY`；平台自身的 Agent 授权或安全拒绝使用 `AUTHORIZATION`。

### 4.4 日志等级

| 等级 | 选择原则 |
|---|---|
| `INFO` | 正常业务中可预期且无需人工介入的受控拒绝 |
| `WARN` | 参数、认证、权限、业务冲突或调用频率问题 |
| `ERROR` | 依赖故障、数据一致性、本系统异常或需要运维关注的问题 |

日志等级与 HTTP 状态、Category 相互独立。禁止仅因为响应为 `4xx` 就不记录，或仅因为响应为 `5xx` 就盲目允许重试。

### 4.5 Retryable

仅当故障是暂态、同一操作具备幂等保障、重试不会重复扣费或产生重复副作用时，`retryable` 才可设为 `true`。

- `retryable=true` 是“允许按策略重试”，不是客户端立即无限重试的命令。
- 支付、创建任务、回调等有副作用操作必须结合幂等键。
- 退避、最大次数和 `retryAfterSeconds` 属于执行策略，不编码到错误码。
- 业务冲突、权限失败、参数错误和安全拒绝通常不可重试。

### 4.6 HTTP 状态选择

| HTTP | 使用边界 |
|---:|---|
| `400` | 请求体无法解析、字段或回调校验失败 |
| `401` | 登录凭据缺失、无效或过期 |
| `403` | 调用方已识别但无权访问 |
| `404` | 指定资源不存在 |
| `405` | 请求方法不受支持 |
| `409` | 资源状态、幂等、余额或业务规则冲突 |
| `413` | 上传内容超过限制 |
| `415` | 媒体类型或请求类型不受支持 |
| `422` | 请求格式有效，但内容在业务或依赖语义上被拒绝 |
| `429` | 平台自身限流、并发或调用次数上限 |
| `500` | 平台自身未分类内部故障 |
| `502` | 依赖调用失败或返回不可解析 |
| `503` | 依赖或平台能力暂不可用 |
| `504` | 依赖响应超时 |

该表用于选择传输语义，不改变“HTTP 与错误码三位序号独立”的原则。供应商返回的 HTTP 状态不能不经分类直接透传为平台状态，例如供应商账户限流可由平台对外收敛为模型服务暂不可用。

### 7.4 迁移约束

部分运行时兼容码目前驱动 `ModelRoutingService` 的熔断、账户健康判断和故障转移。禁止直接全局替换字符串。安全迁移顺序必须是：

1. 定义共享 canonicalizer、Registry allowlist，以及以 `(producer/domain, alias)` 为键的兼容映射表。
2. 定义 typed `failureReason` 契约：允许值、跨服务 DTO 字段、存储位置或仅事件存储、产生/透传/清空生命周期。该步骤完成前，本文表格中的“转为 `failureReason`”只是目标设计，没有可直接写入的统一字段。
3. 把熔断、账户健康和路由判断从公开 `errorCode` 迁移到 typed `failureReason` 与 delivery metadata。
4. 在 Worker callback、Workflow callback 和 Agent Task bridge 增加 allowlist、LEGACY/alias 归一与未知码安全降级。
5. 双写正式 `errorCode` 与内部 `failureReason`，同步消费者和监控。
6. 回填必要历史数据并观察无旧码流量窗口。
7. 最后删除裸字符串生产点和兼容 alias。

供应商的 `HTTP_401`、SDK code、原始 `type` 等只能写 `providerErrorCode`；不得进入 Registry，也不得直接返回浏览器。

## 8. 异常层级与抛出规范

新代码使用以下异常层级：

```text
AppException
├── BizException
├── DependencyException
└── SystemException
```

| 异常 | 使用场景 |
|---|---|
| `BizException` | 可预期的校验、权限外业务规则、资源状态或冲突 |
| `DependencyException` | 模型、支付、对象存储等外部依赖失败 |
| `SystemException` | 本系统配置、存储、一致性或未知内部故障 |
| `BusinessException` | 旧 `ErrorCode` 的兼容适配器；新 V2 代码不应首选 |

业务异常示例：

```java
throw new BizException(
        TaskErrors.TASK_STATE_CONFLICT,
        TaskErrors.TASK_STATE_CONFLICT.defaultUserMessage(),
        "Task state rejected operation; taskId=" + taskId + "; status=" + status,
        null,
        Map.of("taskId", taskId, "status", status)
);
```

依赖异常示例：

```java
throw new DependencyException(
        ModelErrors.RESPONSE_TIMEOUT,
        "Model request timed out; provider=" + provider + "; providerRequestId=" + providerRequestId,
        cause,
        Map.of("provider", provider, "providerRequestId", providerRequestId)
);
```

约束：

- `userMessage` 使用正式定义的默认安全文案，或从受控文案表选择。
- 动态诊断只进入 `developerMessage` 或 `logContext`。
- `logContext` 仅放低风险、结构化、可检索字段；禁止放请求体、凭据和供应商原始正文。
- 不得为传递任意 `details` 而新增异常字段。
- 未分类异常由全局异常处理器收敛为 `SYSTEM_001`，不得把 `exception.getMessage()` 原样回传用户。

## 9. 文案与脱敏规范

### 9.1 userMessage

- 最大长度 200 字符。
- 必须使用简短中文，说明用户能理解且能采取的下一步。
- 不得包含数据库、表名、SQL、Java/Python 类名、堆栈、服务器路径、内部 URL、供应商原文、手机号、账号、密钥、Token、Cookie 或请求体。
- 原则上不插入动态诊断值。余额数、文件限制、重试秒数、字段名和当前状态等动态事实进入 `developerMessage`；如产品确需向用户展示，必须通过独立、经评审的业务接口或静态配置提供，不得恢复错误响应中的 `details`。
- 同一错误码的用户语义必须稳定，不能按抛出点变成互不相关的文案。

### 9.2 developerMessage

- 最大长度 2000 字符。
- 应采用简短的英文或统一格式中文，以 `key=value` 提供必要上下文。
- 可以包含已脱敏的任务 ID、步骤 ID、状态、阈值、重试次数、耗时、供应商代号和 `providerRequestId`。
- 不得包含凭据、Cookie、完整手机号、完整请求/响应正文、SQL、堆栈或 JDBC URL。
- 即使调用方是管理员，仍必须经过 `ErrorMessageSanitizer`；“管理端可见”不等于“允许明文敏感信息”。

推荐示例：

```text
Upload rejected; actualBytes=15728640; maxBytes=10485760; contentType=image/png
```

禁止示例：

```text
SQLException: SELECT * FROM users WHERE phone='133...'; password=...; responseBody={...}
```

SQL、堆栈和供应商原始正文如确需排查，只能进入受访问控制和保留策略约束的服务端日志；凭据和密钥在任何日志中都不得明文记录。

### 9.3 当前日志安全缺口

响应侧已经使用 `ErrorMessageSanitizer`，但当前实现尚不能证明“日志全链路脱敏”：

- `AppException` 会把传入的原始 `developerMessage` 作为异常 message。
- `GlobalExceptionHandler` 的 `ERROR` 分支会再次记录原始 throwable。
- 数据库、Servlet 和未分类异常分支会记录 `rootMessage` 与原始异常对象。

因此敏感值可能绕过结构化参数的脱敏，从异常首行或堆栈重新进入日志。这是现存安全缺口。修复前不得宣称日志已完全满足本节规范；后续必须在异常构造和日志边界统一脱敏、禁止记录未经审查的 `rootMessage`，并增加凭据不会从 throwable 泄漏的定向验证。

## 10. 持久化规范

终态失败记录应原子写入：

```text
error_code
user_message
developer_message
failure_trace_id
```

涉及供应商时另写：

```text
provider_error_code
provider_request_id
```

当前相关表面包括：

- `ai_tasks`、`ai_task_logs`
- `task_model_route_attempts`
- `agent_runs`、`agent_tool_calls`
- `workflow_runs`、`workflow_run_steps`、`workflow_step_attempts`
- `billing_usage_logs` 中的错误码和供应商诊断字段

持久化规则：

1. 新写入的 `error_code` 必须是 Registry 正式码；兼容期确需写旧别名时必须同时有明确迁移任务。
2. 用户投影只读取 `user_message`；管理投影才可读取脱敏后的 `developer_message`。
3. `error_message` 是旧诊断兼容字段，不应成为新代码的唯一真源。
4. 成功、重新开始或重试进入新 attempt 时，必须清空上一轮失败字段，避免旧错误污染当前状态。
5. 供应商原码与平台正式码分列保存，禁止互相覆盖。
6. `failure_trace_id` 最长 64，并建立适合排查的索引。
7. 历史迁移脚本不可重写；修复历史数据必须新增前向迁移。

`sql/118_error_contract_phase1.sql` 曾从旧 `error_message` 回填诊断字段，`sql/120_error_contract_legacy_diagnostic_cleanup.sql` 已做前向清理。后续禁止将未知来源的 `error_message` 无条件回填为 `developerMessage`。

## 11. TraceId、日志与监控

### 11.1 TraceId

- HTTP 入口接收符合 `[A-Za-z0-9_-]{1,64}` 的 `X-Request-Id`；缺失或非法时生成 UUID。
- TraceId 必须写入 MDC、响应头、V2 响应、跨服务请求/回调和失败记录。
- 入口有请求上下文时必须生成并透传；只有脱离请求上下文的历史或异步记录可以为空。
- `failureTraceId` 表示失败发生处的 TraceId，不得用供应商 requestId 替代。

### 11.2 结构化日志

应用异常日志统一包含：

```text
errorCode=<canonical-code> traceId=<trace-id> developerMessage=<sanitized-text>
```

日志级别使用错误定义中的 `logLevel`。`ERROR` 级可以记录服务端异常对象，但面向响应的 `developerMessage` 必须保持脱敏且不含堆栈。

### 11.3 Loki 与指标

- 只有 Registry 中的 canonical `error_code` 才是低基数字段，可以作为 Loki label 和指标维度。
- `trace_id` 是高基数字段，只作为日志内容提取和查询，禁止作为 label。
- `developerMessage`、`providerRequestId`、用户 ID、任务 ID 不得作为 Prometheus label。
- Grafana 应按正式码聚合失败量、失败率和趋势，并支持通过 TraceId/ErrorCode 跳转日志。
- 必须监控未知错误码、`SYSTEM_001`、依赖错误率、客户端契约解析失败和 LEGACY/V2 流量比例。

建议告警维度只使用稳定的 `errorCode`；更细的 `failureReason` 可进入日志或受控低基数指标，但不得污染公开错误码体系。

当前 Alloy 使用宽松正则提取所有大写下划线值，并直接设置 `error_code` label，尚未校验三位格式或 Registry allowlist。结合第 7 节的裸码现状，当前标签并不保证低基数，这是观测配置缺口。完成 canonicalization 前必须采用以下一种受控方案：

1. 从 Registry 生成并随配置发布 canonical allowlist，只为命中值设置 `canonical_error_code` label；或
2. 仅保留原值为日志提取字段，不设 label，同时对未知码做独立低基数计数和告警。

禁止把未知原值本身作为告警 label，否则每个动态值都可能扩大时序和 Loki stream 基数。

当前尚未发现统一的“客户端契约解析失败”和“LEGACY/V2 流量比例”指标或 Grafana 面板。这两项是待建设的 V2 发布门禁，不是已完成能力；在生产切换 V2 前必须先落地并验证。

## 12. 新增与扩展流程

### 12.1 设计步骤

新增错误码必须按顺序完成：

1. **确认语义**：描述触发条件、责任服务、用户能否修复、是否暂态、是否有副作用。
2. **查重**：检索 Registry、本文目录、LEGACY 映射、运行时兼容表和 Git 历史，优先复用语义完全一致的正式码。
3. **确定模块**：使用已有业务边界；只有确有独立所有者时才创建新前缀。
4. **保留编号**：选择该模块从未使用的三位序号。已删除、废弃和历史发布过的编号也视为占用。
5. **定义元数据**：同时确定 HTTP、默认用户文案、Category、日志等级和 Retryable，不得只增加字符串常量。
6. **注册**：在模块枚举中实现 `ErrorDefinition`；新模块枚举必须显式加入 `ErrorDefinitionRegistry.buildDefinitions()`。
7. **接入异常**：在产生点使用正确的 `AppException` 子类，动态上下文进入 `developerMessage`/`logContext`。
8. **处理兼容**：明确 LEGACY 降级映射、跨服务 alias、旧客户端读取方式和历史数据迁移。
9. **同步契约**：更新 OpenAPI、本文正式码目录、前端安全文案映射、Worker/Agent 客户端和管理端投影。
10. **接入观测**：确认日志使用 canonical code，补充必要的指标、Grafana 聚合和告警说明。
11. **验证与发布**：执行与风险相称的定向测试，先升级消费者，再切生产 V2 开关。

### 12.2 Definition 示例

以下仅展示结构，不表示预留了示例编号：

```java
EXAMPLE_FAILURE(
        "MODULE_001",
        HttpStatus.CONFLICT,
        "当前状态无法完成该操作",
        ErrorCategory.BUSINESS,
        ErrorLogLevel.WARN,

```

throw new RuntimeException("MODULE_TIMEOUT");
```

String errorCode = "TASK_" + status;
```

## 13. 验证要求

验证范围必须与变更风险和触点相称，不为局部新增错误码机械运行全链路或全量回归。

### 13.1 基础必测

每个正式错误码变更至少验证：

1. 格式合法、全局唯一，且新定义实际出现在 `ErrorDefinitionRegistry.all()`。
2. 正式码与 HTTP 状态、Category、LogLevel、Retryable 和默认文案符合设计。
3. 受影响的响应壳字段白名单正确，用户壳不含 `message`、`data`、`details`、`developerMessage`。
4. 受影响异常的用户文案安全，动态诊断不进入用户响应。

Registry 只能校验“已经注册的集合”；新枚举若忘记加入 Registry，不会自动被发现，因此第 1 项必须显式覆盖新枚举的可发现性。

### 13.2 按触点验证

仅在变更触及相应边界时增加：

- 修改管理/内部可见性时，验证认证管理员、管理登录、未认证管理请求和未验签内部请求。
- 修改文案或脱敏器时，验证 200/2000 字符截断、响应脱敏和 throwable 日志不泄漏。
- 修改 LEGACY mapper 或响应切换时，验证 LEGACY 不变和 V2 转换。
- 修改跨服务 DTO/解析时，验证 Worker、Agent Service、用户端或管理端中的实际受影响消费者。
- 修改持久化时，验证失败字段落库、成功/重试清理和用户/管理投影；有迁移时使用真实 MySQL。
- 修改 TraceId 传播时，验证受影响入口、回调、数据库和日志的真实链路。

涉及数据库迁移、跨服务契约或生产开关属于高风险变更：迁移必须在真实 MySQL 验证并可重复执行；部署后必须进行受控真实链路验收。未执行生产链路时只能报告“代码验证通过，生产未验收”。

## 14. 发布与回滚

从 LEGACY 切换 V2 的顺序：

1. 先部署可同时读取 LEGACY 与 V2 的用户端、管理端、Worker 和 Agent Service。
2. 部署双写正式失败字段和 TraceId 的 Backend。
3. 在测试或灰度环境验证普通用户、认证管理员、管理登录和未验签内部调用的字段可见性。
4. 单独切换 `APP_ERROR_CONTRACT_MODE=V2`。
5. 观察未知码、5xx、前端解析失败、错误码分布和跨服务 callback。
6. 若异常仅来自响应壳或客户端解析，首选回切 `LEGACY`，并保留新增列和双读能力；若属于应用逻辑、权限投影或跨服务回调回归，仍应按不可变镜像回滚应用版本。禁止回滚已经执行的前向数据库列或迁移历史。

禁止在同一次发布中同时“切换 V2”和“删除 Legacy mapper、旧字段或兼容解析”。移除兼容能力必须有明确的无旧流量观察窗口。

## 15. 废弃、别名与编号不可复用

- 已发布错误码的业务语义永久稳定，禁止改名、重排或复用编号。
- 废弃码继续保留为 Registry 定义或明确 tombstone，直到所有在线流量、数据库历史和客户端版本均不再依赖。
- `defaultUserMessage` 可以做不改变语义的安全或措辞修正；HTTP、Category、Retryable 和核心语义的变化必须按契约变更评审。
- 同一 `(producer/domain, alias)` 在兼容映射表中只能归一到一个明确正式码，不得由各服务自行解释。若同一裸字符串跨多个领域代表不同投影，必须先转换为 typed 内部 `failureReason`，再由显式资源投影规则生成正式码；此时禁止继续把裸字符串当作全局 alias。
- 未知入站码必须记录受控告警并降级为安全正式码，禁止原样返回用户或成为新的 Loki label。
- 供应商码永远不占用平台业务编号。

## 16. 评审清单

合并前逐项确认：

- [ ] 使用 Registry 正式码，没有新增裸字符串或动态拼码。
- [ ] 编号在当前代码、文档和 Git 历史中均未被使用。
- [ ] HTTP、Category、LogLevel、Retryable 相互独立且理由成立。
- [ ] `userMessage` 简短、安全、无动态敏感信息。
- [ ] `developerMessage` 和 `logContext` 已脱敏，不含请求体、SQL、堆栈或凭据。
- [ ] 用户、管理员、管理登录和内部签名边界均正确。
- [ ] LEGACY 降级、跨服务解析和 alias 归一已定义。
- [ ] 供应商错误使用独立 `providerErrorCode` / `providerRequestId`。
- [ ] 失败字段原子写入，成功和重试会清理旧失败字段。
- [ ] OpenAPI、本文码表、消费者映射和监控已同步。
- [ ] 定向测试与必要真实链路验收范围已说明。
- [ ] 发布顺序、观察指标和回滚方式明确。
