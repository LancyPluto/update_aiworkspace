# AI Tool Market 下阶段开发计划

周期：4-8 周  
目标：停止功能漂移，压实主链路、安全边界和可计费稳定性。  
状态刷新：2026-07-01

> 2026-07-01 更新：P0 已完成第一轮代码落地，本文继续作为 P1/P2 规划和剩余 P0 人工项追踪使用。P0 完成状态以 [优化清单-2026-06-02.md](./优化清单-2026-06-02.md) 与 [商业上线P0发布门禁-2026-06-30.md](./商业上线P0发布门禁-2026-06-30.md) 为准。

## 1. 路线图总览

下一阶段不追求新增大功能。核心目标是让平台具备可运营、可审计、可计费、可持续交付的基础。

优先级定义：

- P0 紧急：不做会影响安全、计费、任务稳定性或上线信任。
- P1 重要：不做会持续拖慢交付或放大回归风险。
- P2 优化：提升运营效率、用户体验和数据观察能力。

## 2. P0 紧急：第 1-2 周

### 2.1 密钥和证书出库

- [状态更新] `.env`、`WXcert/*.pem`、`_remote.py`、`_fix_remote.py` 已从 Git 索引移除并加入忽略规则；仍需人工轮换所有可能暴露过的密钥和证书。
- [问题本质] 支付证书、远程凭据和运行密钥属于最高优先级安全资产，不能进入源码仓库。
- [后果预估] 证书泄露、内部接口伪造、支付风险、客户尽调失败。
- [具体行动建议] 从 git 移除真实敏感文件，保留 `.env.example`；轮换所有可能泄露的支付证书、内部 token、部署密码和模型 key；补充 `.gitignore`；新增安全启动检查。

验收标准：

- `git ls-files .env WXcert _remote.py _fix_remote.py` 不返回真实敏感文件。
- 后端、Agent、Worker 在生产环境下遇到默认 token 或占位 key 必须拒绝启动。
- 文档明确本地密钥放置方式和生产密钥注入方式。

### 2.2 统一任务队列事实源

- [状态更新] 后端与 Worker 默认任务队列已统一为 RabbitMQ；Redis consumer 仅保留本地开发或历史兼容，生产环境显式配置 Redis 队列会启动失败。
- [问题本质] 队列事实源不统一会破坏任务状态、重试、死信和额度对账。
- [后果预估] 任务重复、任务丢失、额度冻结不释放、客服成本上升。
- [具体行动建议] 生产默认 RabbitMQ；Redis 队列只保留本地开发或兼容模式；更新 README、Worker 配置、Docker Compose 和测试说明。

验收标准：

- 生产配置只启用 RabbitMQ。
- 死信重放、重复回调、任务取消、失败释放额度有自动化测试。
- Worker 启动日志明确当前队列后端。

### 2.3 固化任务与额度状态机

- [现状描述] 任务执行、Worker 回调、Agent 工具调用、PPT 长任务都涉及冻结、执行、成功扣费、失败释放。
- [问题本质] 状态机如果散落在不同服务中，计费就不可审计。
- [后果预估] 用户被多扣、少扣、冻结不释放或结果不展示，直接伤害付费信任。
- [具体行动建议] 在后端定义统一状态机文档和测试矩阵；所有 Worker、Agent、PPT 任务都通过同一套内部回写语义；补超时对账策略。

验收标准：

- 覆盖 `CREATED -> PROCESSING -> SUCCESS`、`CREATED -> PROCESSING -> FAILED`、取消、超时、重复 success、重复 failed。
- 信用流水只产生一次有效结算。
- 失败和超时必须释放冻结额度。

### 2.4 停产 legacy 和 mock 生产路径

- [状态更新] 旧 ai-tools 接口已加废弃日志；PPT 新写入已改为 `tool-integration`，旧 `ppt-workflow` 只读兼容；mock 管理登录和前端 mock 工具数据已限制为显式开发开关。缺 `toolCode` 的少数 PPT 入口仍需继续收口。
- [问题本质] 这些兼容路径继续存在，会扩大安全面和维护面。
- [后果预估] 配置不一致、生产误用 mock、旧接口继续被新代码依赖。
- [具体行动建议] 标记废弃、加运行日志、加后台提示，禁止新增调用；生产环境关闭 mock 支付和 mock 登录；PPT 创建强制带 `toolCode`。

验收标准：

- 管理端和用户端不再新增旧 ai-tools 调用。
- 生产环境 mock 支付入口不可用。
- PPT 新建链路必须携带明确工具标识。

## 3. P1 重要：第 3-5 周

### 3.1 拆分巨型服务

目标文件：

- `AgentRunServiceImpl.java`
- `CommunityServiceImpl.java`
- `ToolServiceImpl.java`
- `deep_agents_engine.py`

拆分原则：

- 不重写业务，只拆职责。
- 先抽状态机、事件写入、设置解析、工具调用、上下文构造。
- 每拆一个职责就补对应单元测试。

产品价值：

- 降低改动风险。
- 提高新工具、新 Agent 策略、新社区事件的交付速度。
- 减少核心链路回归。

验收标准：

- 核心服务单文件行数明显下降。
- 原有后端和 Agent 测试通过。
- 新增职责模块有独立测试。

### 3.2 拆分巨型前端页面

目标文件：

- `user-web/src/pages/AgentHome/AgentChatPane.vue`
- `user-web/src/pages/Dashboard/Page.vue`
- `admin-frontend/app/tools/page.tsx`
- `admin-frontend/app/prompts/page.tsx`

拆分原则：

- 页面只负责编排。
- API 调用、表单状态、事件流、工具确认、附件上传、结果渲染分离。
- 管理端高风险配置组件必须具备测试/预览/保存状态。

产品价值：

- 前端交互改动更快。
- 管理后台配置错误更少。
- Agent 和 Dashboard 体验可独立优化。

验收标准：

- 用户端 `npm run build` 通过。
- 管理端 `npm run build` 和 `npm run typecheck` 通过。
- 主要页面没有明显交互回归。

### 3.3 统一工具配置模型

- [现状描述] 工具字段、Prompt、模型配置、工作流、集成插件、PPT 配置和兼容 marker 分散存在。
- [问题本质] 工具是商业单元，但配置模型被拆成多个历史层。
- [后果预估] 工具上线慢，配置容易错，运营无法独立完成工具维护。
- [具体行动建议] 明确工具配置的唯一结构：基础信息、输入字段、执行处理器、模型绑定、计费规则、结果渲染、集成扩展。旧字段迁移到新结构后停止写入。

验收标准：

- 新工具上线只需要一套配置入口。
- 配置导入导出不再混入旧 marker。
- 工具详情、任务创建、Agent 工具描述读取同一配置源。

### 3.4 建立黄金链路测试

必须覆盖 5 条链路：

1. 文本工具任务：创建、执行、成功、扣费、结果展示。
2. 图片工具任务：创建、落盘、回写、扣费、画廊展示。
3. 视频或数字人任务：长任务轮询、超时、失败释放。
4. Agent 调用工具：意图识别、缺参、确认、任务创建、事件回传。
5. 社区同款创作：作品详情、同款计数、Dashboard 预填、任务创建、归因事件。

验收标准：

- 每条链路都有自动化或半自动化命令。
- 失败时能定位到后端、Agent、Worker、前端或配置问题。
- 作为每轮发布前检查项。

### 3.5 补社区归因闭环

- [现状描述] 社区已具备发现、详情、收藏、同款，但转化归因还需要更稳定地记录 `task_created` 和 `credit_spent`。
- [问题本质] 社区如果不能证明带来消费，就会变成成本中心。
- [后果预估] 运营无法判断哪些工具、话题、作者和案例真正贡献收入。
- [具体行动建议] 稳定 `sourcePostId` 透传；任务创建和扣费时写社区事件；后台展示工具维度和作品维度转化数据。

验收标准：

- 从社区同款进入 Dashboard 后创建任务，后端能关联原作品。
- 扣费成功后能形成 `credit_spent` 归因。
- 后台能看到作品带来的同款任务和消费。

## 4. P2 优化：第 6-8 周

### 4.1 工具详情页展示社区案例

目标：

- 每个工具详情页展示该工具精选社区作品。
- 用户可以从案例直接同款创作。

产品价值：

- 降低用户首次使用门槛。
- 提高工具转化率。

验收标准：

- 工具详情页展示公开且审核通过作品。
- 无作品时不展示空壳模块。
- 同款链路复用社区归因逻辑。

### 4.2 素材库和灵感收藏筛选

目标：

- 素材库按工具、模态、时间、任务状态筛选。
- 灵感收藏按工具、话题、模态筛选。

产品价值：

- 用户更容易找到历史结果。
- 提高复用和再次消费概率。

验收标准：

- 筛选条件不破坏现有分页和预览。
- 私有素材和社区收藏边界清晰。

### 4.3 管理后台信息架构调整

目标分区：

- 运营日常：工具上下架、社区审核、用户与充值。
- 模型与成本：模型配置、价格、余额链接、计费日志。
- 工具配置：字段、Prompt、结果渲染、集成。
- 运行诊断：任务、Agent runs、队列、错误。
- 系统设置：安全、CORS、客服、导入导出。

产品价值：

- 降低运营误操作。
- 提高工具上线效率。

验收标准：

- 高风险操作有确认和回滚。
- 常用运营路径不超过 3 次点击。

### 4.4 监控看板

关键指标：

- 任务成功率
- 平均执行时长
- Worker 回调失败数
- 死信队列数量
- 冻结未释放额度
- Agent 工具调用成功率
- 社区同款转化率
- 模型成本与收入差

产品价值：

- 把“感觉系统不稳”变成可定位指标。
- 支持商业化成本控制。

验收标准：

- 后台至少展示核心健康指标。
- P0 指标异常有日志或告警入口。

## 5. 发布节奏

第 1 周：

- 密钥出库已完成；密钥轮换仍需人工在支付平台、模型平台、服务器和 GitHub Secrets 中执行。
- 生产默认值校验已覆盖后端、Agent Service、Worker。
- mock 生产路径已完成第一轮关闭，后续保持回归测试。

第 2 周：

- 队列事实源已统一为 RabbitMQ 生产默认。
- 任务/额度状态机已补取消后 failed、超时对账等关键测试，仍需黄金链路长期验收。
- legacy 调用已完成第一轮废弃标记，缺 `toolCode` 入口继续收口。

第 3-4 周：

- 拆分后端和 Agent 巨型模块。
- 建立黄金链路测试。

第 5 周：

- 拆分前端巨型页面。
- 工具配置模型收敛方案落地第一版。

第 6-8 周：

- 社区归因闭环。
- 工具详情案例入口。
- 管理端信息架构和监控看板。

## 6. 禁止事项

在 P0 完成前，禁止：

- 新增模型族。
- 新增社区社交能力。
- 新增复杂推荐。
- 新增工作流画布能力。
- 新增未覆盖扣费和失败释放的任务类型。
- 新增旧接口兼容。

在 P1 完成前，禁止：

- 继续扩大巨型页面和巨型服务。
- 把新 Agent 能力直接塞进现有运行主类。
- 把新工具配置写进 `configNote` 的非结构化兼容块。

## 7. 成功标准

4-8 周后，项目应达到：

- 敏感文件不在 git 中。
- 生产环境无法用默认密钥启动。
- 任务和额度状态机可审计。
- 队列事实源明确。
- 旧接口和 legacy marker 进入退场流程。
- 5 条黄金链路可回归。
- Agent 工具调用稳定服务任务消费。
- 社区能证明同款创作带来任务和算力消费。
- 团队新增功能前能先判断是否强化主链路。
